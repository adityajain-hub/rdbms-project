Executive Summary

In large university campuses like Manipal University Jaipur with over 15,000 students and staff, hundreds of valuable personal items—such as laptops, smartwatches, calculators, college ID cards, keys, and wallets—are lost each semester. Traditional lost-and-found mechanisms rely on fragmented physical registers at security checkpoints or informal social media messages, leading to low recovery rates, administrative overhead, and fraudulent ownership claims.

This project introduces the Campus Lost & Found Management System, a relational database application designed to enforce structured data integrity, secure role-based access, and automated verification workflows. The solution is strictly modeled in Third Normal Form (3NF) and integrates MySQL 8.0 features including multi-table JOIN operations, an abstracted VIEW, an automated TRIGGER, a transaction-controlled STORED PROCEDURE, and a live activity_logs audit trail.

1. Introduction & Problem Statement

The primary objectives of this laboratory project are to address the following critical challenges in campus asset recovery:

  • Lack of Centralized Record Keeping: Physical logbooks maintained across separate academic blocks, libraries, and hostels fail to cross-reference items found in one block with lost reports filed in another.
  • Absence of Verifiable Claim Proof: Handing over high-value electronics without recorded verification proof creates liabilities and potential property misappropriation.
  • Redundant Duplicate Listings: Finders who want to alert an owner often create duplicate records rather than directly matching the owner's existing lost listing.
  • Audit Trail Deficits: Campus security administration requires an unalterable log of who reported, claimed, approved, and verified the recovery of each item.

2. System Architecture & Dual-Engine Strategy

The system follows an industry-standard Three-Tier Architecture, engineered to guarantee 100% operational availability during academic viva and laboratory demonstrations:

  1. Presentation Layer (Frontend): Developed with HTML5, CSS3, and modern Vanilla JavaScript. Implements a desktop-grade 3-panel workspace (Filter Sidebar, Grid Deck, and Deep Inspector) with responsive Dark/Light themes and zero external heavyweight UI dependencies.
  2. Application Layer (Backend): Built using Python 3 and the lightweight Flask REST framework. Implements 10 REST endpoints providing CORS headers, file sanitization via Werkzeug, input validation, and transaction management.
  3. Data Tier (Dual-Database Failover Engine):
    • Primary Engine: MySQL 8.0 Server (InnoDB storage engine) providing ACID guarantees, foreign key cascades, triggers, and stored procedures.
    • Zero-Config SQLite Failover: If MySQL is unavailable on an evaluation machine, the backend seamlessly switches to an embedded SQLite database (`campus_demo.db`), preserving table schemas, triggers, and mock auth sessions without any crashes.
Lab Innovation Note: The connection manager in backend/app.py probes MySQL upon startup. If MySQL connects, the status bar displays MySQL 8.0 (Live DB). If offline, it smoothly switches to SQLite, guaranteeing uninterrupted examiner demonstrations.

5. Relational Schema & Normalization Analysis (3NF)

Database normalization systematically decomposes relations to minimize data redundancy and eliminate insert, update, and delete anomalies.

5.1 First Normal Form (1NF) Compliance

A relation is in 1NF if and only if all domain values are atomic (indivisible) and no repeating groups exist. In our schema:

  • All attributes (e.g. email, location, date_incident) contain singular, atomic scalars.
  • Multiple contact numbers or item tags are never stored as comma-delimited strings in a single tuple.
  • Each relation has a defined primary key ensuring tuple uniqueness.

5.2 Second Normal Form (2NF) Compliance

A relation is in 2NF if it is in 1NF and every non-prime attribute is fully functionally dependent on the entire primary key (no partial key dependencies).

  • Every table in our database employs a single-column surrogate primary key (user_id, category_id, item_id, claim_id, log_id).
  • Because no composite primary keys exist, partial dependencies are mathematically impossible: $$\forall X \rightarrow Y, \quad X \text{ is a single-attribute key} \implies Y \text{ cannot depend on a proper subset of } X.$$

5.3 Third Normal Form (3NF) Compliance

A relation is in 3NF if it is in 2NF and no non-prime attribute is transitively dependent on the primary key (no $X \rightarrow Y \rightarrow Z$ where $Z$ is non-prime).

  • Elimination of Category Transitivity: In an unnormalized schema, storing category_name inside items creates the functional dependency chain: $$\text{item\_id} \rightarrow \text{category\_id} \rightarrow \text{category\_name}$$ Here, category_name transitively depends on item_id through category_id. If all items in a category are deleted, the category itself is lost (deletion anomaly).
  • Resolution: We decomposed categories into an independent categories(category_id, category_name) table. The items table references category_id as a foreign key, completely satisfying 3NF.

6. Advanced SQL Implementation Details

6.1 Multi-Table INNER JOIN (Item Board Retrieval)

Joins three tables simultaneously to yield complete human-readable listings without exposing foreign key integers: 

SELECT i.item_id, i.report_type, i.title, i.description,
       c.category_name, i.location, i.date_incident, i.image_url, i.status,
       u.full_name AS reported_by_name, u.phone AS contact_phone
FROM   items i
JOIN   categories c ON i.category_id = c.category_id
JOIN   users u      ON i.reported_by  = u.user_id
WHERE  i.status != 'RESOLVED'
ORDER  BY i.item_id DESC;

6.2 Database View (`vw_active_items` — Syllabus Lab 10)

Encapsulates the complex join logic into a virtual relation for clean query reuse: 

CREATE VIEW vw_active_items AS
SELECT i.item_id, i.report_type, i.title, i.description,
       c.category_name, i.location, i.date_incident, i.image_url, i.status,
       u.full_name AS reported_by_name, u.phone AS contact_phone
FROM   items i
JOIN   categories c ON i.category_id = c.category_id
JOIN   users u      ON i.reported_by  = u.user_id
WHERE  i.status != 'RESOLVED';

6.3 Automated Database Trigger (`trg_resolve_item_on_claim` — Syllabus Lab 12)

Automatically marks an item as RESOLVED and writes an audit record when an ownership claim is marked APPROVED: 

DELIMITER $$
CREATE TRIGGER trg_resolve_item_on_claim
AFTER UPDATE ON claims
FOR EACH ROW
BEGIN
    IF NEW.status = 'APPROVED' AND OLD.status != 'APPROVED' THEN
        -- 1. Automatically update item status to RESOLVED
        UPDATE items 
        SET status = 'RESOLVED' 
        WHERE item_id = NEW.item_id;

        -- 2. Automatically log to audit trail
        INSERT INTO activity_logs (action_type, details)
        VALUES ('CLAIM_APPROVED', CONCAT('Claim #', NEW.claim_id, ' approved for Item #', NEW.item_id));
    END IF;
END$$
DELIMITER ;

6.4 Stored Procedure with Transaction Control (`sp_approve_claim`)

DELIMITER $$
CREATE PROCEDURE sp_approve_claim(IN p_claim_id INT)
BEGIN
    START TRANSACTION;
        UPDATE claims SET status = 'APPROVED' WHERE claim_id = p_claim_id;
    COMMIT;
END$$
DELIMITER ;

7. Records Archive & System Audit Trail

A crucial requirement of enterprise asset tracking is maintaining an immutable audit log of all system transitions. When items are recovered or handed over, they are completely removed from active browsing decks and transferred to the Records system.

7.1 Two-Tier Records Navigation

  • Sub-Tab 1: Resolved Belongings Archive: Displays cards of all items whose status has transitioned to RESOLVED. Each card highlights verified handover completion, date, category, and inspector notes.
  • Sub-Tab 2: Audit & Activity Logs: Renders a tabular display directly populated from the activity_logs table in MySQL. Includes a live client-side keyword filter to instantly filter actions by type, user, or item ID.

9. Conclusion & Future Scope

9.1 Project Conclusion

The Campus Lost & Found Relational Database Management System successfully fulfills all requirements outlined in the Manipal University Jaipur RDBMS Laboratory (CSC2131) curriculum.

Through practical implementation, the project demonstrates:

  • Sound theoretical schema design complying with 1NF, 2NF, and 3NF normal forms.
  • Complex relational querying using multi-table INNER JOIN, LEFT JOIN, and UNION.
  • Database abstraction through a pre-joined View (vw_active_items).
  • Business rule automation via an active database Trigger (trg_resolve_item_on_claim).
  • Transaction Control Language (TCL) execution using a Stored Procedure (sp_approve_claim).
  • Role-Based Access Control protecting sensitive claim and recovery actions.
  • Dual-database resilience guaranteeing smooth project presentation under any evaluation conditions.

9.2 Future Scope & Planned Enhancements

While the current application is fully functional and ready for deployment across campus security kiosks, the following enhancements are envisioned for future production releases:

  1. QR Code Tagging System: Enable students to generate and print unique QR code stickers for personal belongings (e.g. laptops, water bottles) linked to their anonymous student ID in the database.
  2. Computer Vision Similarity Matching: Implement a feature extraction model using perceptual hashes or deep embeddings (e.g. ResNet) to automatically calculate visual similarity scores between uploaded lost and found photos.
  3. Push & SMS Notifications: Integrate campus SMS gateways or Telegram bots to alert students immediately when a handover notice or matching item is logged.
  4. Geographical Campus Heatmaps: Aggregate location data using MySQL spatial extensions to visualize campus loss hotspots on an interactive MUJ map.
