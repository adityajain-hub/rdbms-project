1. Introduction

This project builds a Campus Lost & Found Management System — a web application for Manipal University Jaipur (MUJ) that centralizes reporting and recovery of misplaced items. Students and staff can log lost or found belongings, browse active reports, and submit ownership claims that are verified by a campus admin before the item is returned. The system is backed by a MySQL 8.0 relational database that demonstrates 3NF normalization, multi-table JOINs, a database View, a Trigger, and a Stored Procedure.

2. Functional Overview

The platform consists of the following key modules:

  • Item Reporting: Any campus member can log a LOST or FOUND item with title, description, category, location, and date.
  • Browse & Search: Users can filter the live item board by type (Lost/Found) or category, and search by keyword.
  • Ownership Claims: A finder of an item lists it as FOUND; the true owner submits an ownership claim with identifying proof.
  • Admin Verification: An admin reviews pending claims and approves or rejects them. On approval, a database trigger automatically marks the item as RESOLVED and writes an audit entry.
  • Live Dashboard: Summary counters (Total / Lost / Found / Resolved) update in real time via REST API aggregation queries.

3. System Architecture

The project follows the classic three-tier architecture:

  1. Presentation Layer: HTML5, CSS3, and Vanilla JavaScript (3-panel desktop dashboard).
  2. Application Layer: Python 3 with Flask — 8 clean REST endpoints that execute raw SQL.
  3. Data Layer: MySQL 8.0 (InnoDB) with automatic SQLite fallback for offline demo mode.

5. Database Schema

Below are the complete CREATE TABLE definitions for all five tables in the campus_lost_and_found database.

Users Table

CREATE TABLE users (
    user_id   INT AUTO_INCREMENT PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    email     VARCHAR(100) NOT NULL UNIQUE,
    phone     VARCHAR(20)  NOT NULL,
    password  VARCHAR(100) NOT NULL,
    role      ENUM('STUDENT','FACULTY','STAFF','ADMIN') DEFAULT 'STUDENT'
);

Categories Table

CREATE TABLE categories (
    category_id   INT AUTO_INCREMENT PRIMARY KEY,
    category_name VARCHAR(50) NOT NULL UNIQUE
);

Items Table

CREATE TABLE items (
    item_id       INT AUTO_INCREMENT PRIMARY KEY,
    report_type   ENUM('LOST','FOUND') NOT NULL,
    title         VARCHAR(100) NOT NULL,
    description   TEXT NOT NULL,
    category_id   INT NOT NULL,
    location      VARCHAR(100) NOT NULL,
    date_incident DATE NOT NULL,
    image_url     VARCHAR(255) DEFAULT 'images/laptop.jpg',
    status        ENUM('ACTIVE','CLAIM_PENDING','RESOLVED') DEFAULT 'ACTIVE',
    reported_by   INT NOT NULL,
    FOREIGN KEY (category_id) REFERENCES categories(category_id),
    FOREIGN KEY (reported_by) REFERENCES users(user_id)
);

Claims Table

CREATE TABLE claims (
    claim_id         INT AUTO_INCREMENT PRIMARY KEY,
    item_id          INT NOT NULL,
    claimant_name    VARCHAR(100) NOT NULL,
    claimant_contact VARCHAR(50)  NOT NULL,
    proof_details    TEXT NOT NULL,
    status           ENUM('PENDING','APPROVED','REJECTED') DEFAULT 'PENDING',
    FOREIGN KEY (item_id) REFERENCES items(item_id) ON DELETE CASCADE
);

Activity Logs Table

CREATE TABLE activity_logs (
    log_id      INT AUTO_INCREMENT PRIMARY KEY,
    action_type VARCHAR(50)  NOT NULL,
    details     VARCHAR(255) NOT NULL,
    log_time    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

6. Implementation Details

6.1 Multi-Table JOIN — Item Listing

The main item board fetches data from three tables in a single query using INNER JOINs, eliminating the need to expose raw foreign key IDs to the frontend:

SELECT i.item_id, i.report_type, i.title, i.description,
       c.category_name, i.location, i.date_incident, i.image_url, i.status,
       u.full_name AS reported_by_name, u.phone AS contact_phone
FROM   items i
JOIN   categories c ON i.category_id = c.category_id
JOIN   users u      ON i.reported_by  = u.user_id
ORDER  BY i.item_id DESC;

6.2 Database View — vw_active_items

A reusable VIEW pre-joins all active items so the dashboard can query SELECT * FROM vw_active_items without repeating JOIN logic:

CREATE VIEW vw_active_items AS
SELECT i.item_id, i.report_type, i.title, c.category_name,
       i.location, i.date_incident, i.image_url, i.status,
       u.full_name AS reported_by_name
FROM   items i
JOIN   categories c ON i.category_id = c.category_id
JOIN   users u      ON i.reported_by  = u.user_id
WHERE  i.status != 'RESOLVED';

6.3 Trigger — Auto-Resolve on Claim Approval

When an admin updates a claim's status to APPROVED, the following AFTER UPDATE trigger fires automatically — no extra application code required:

CREATE TRIGGER trg_resolve_item_on_claim
AFTER UPDATE ON claims FOR EACH ROW
BEGIN
    IF NEW.status = 'APPROVED' AND OLD.status != 'APPROVED' THEN
        UPDATE items SET status = 'RESOLVED'
        WHERE  item_id = NEW.item_id;

        INSERT INTO activity_logs (action_type, details)
        VALUES ('CLAIM_APPROVED',
                CONCAT('Claim #', NEW.claim_id,
                       ' approved for Item #', NEW.item_id));
    END IF;
END;

6.4 Stored Procedure — sp_approve_claim

A stored procedure wraps the approval in a transaction, demonstrating TCL (Transaction Control Language):

CREATE PROCEDURE sp_approve_claim(IN p_claim_id INT)
BEGIN
    START TRANSACTION;
        UPDATE claims SET status = 'APPROVED'
        WHERE  claim_id = p_claim_id;
    COMMIT;
END;

6.5 Aggregate Query — Dashboard Statistics

SELECT COUNT(*) AS total_items,
       SUM(report_type = 'LOST')  AS total_lost,
       SUM(report_type = 'FOUND') AS total_found,
       SUM(status = 'RESOLVED')   AS total_resolved
FROM   items;

Normalization (3NF)

The database satisfies all three normal forms:

  • 1NF: All columns hold atomic values; no repeating groups exist.
  • 2NF: Every non-key attribute depends fully on its table's single-column primary key (no partial dependency).
  • 3NF: No transitive dependencies. category_name was moved to the categories table so that item_id → category_id → category_name is eliminated; items now only store the foreign key category_id.

7. Conclusion

This project delivers a fully functional, database-driven Lost & Found portal for MUJ campus. It demonstrates the complete RDBMS lab syllabus — DDL/DML operations, multi-table JOINs, a database View, an AFTER UPDATE Trigger with automatic audit logging, and a Stored Procedure using transaction control. The application uses a dual-database strategy (MySQL 8.0 primary / SQLite offline fallback) ensuring the project works reliably even during a lab demonstration without MySQL access.

8. Future Enhancements

Some planned additions to extend the platform include:

  • User Authentication: Secure login with hashed passwords and session tokens.
  • Image Upload: Allow reporters to attach photos of items for faster identification.
  • Email Notifications: Send automated email alerts when a matching item is reported.
  • Admin Dashboard: Full analytics view — items by category, resolution rate, average time to resolve.
  • Mobile App: React Native front-end connecting to the existing Flask REST API.
  • Enhanced Security: Role-based access control (RBAC) using MySQL DCL (GRANT / REVOKE).
